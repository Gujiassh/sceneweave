# 模块化审查：先修正持久化边界

基线为 `main@0c5de5d`。结论是保留当前公开包方向，并先修正活动快照到持久化输入的合同。审查只提出一个有充分证据的重构候选，没有以文件行数填充候选数量。

## 候选：显式转换当前文档的保存输入

影响高，证据为[代码健康审查](code-health.md)中的真实组合失败。活动快照同时保存文档、项目元数据与可用模型字节；历史只恢复文档，仓储却把全部可用字节理解为当前文档的严格输入集。一个移除资产的历史操作因此需要了解两个模块的不同政策。

目标关系是：`历史文档 + 保留资源池 → 当前引用持久化投影 → repository.save`。活动池或已入库字节仍供 renderer 和 redo 使用。仓储继续负责严格 SHA、引用和原子事务校验。该方案是私有转换边界，无须新的服务框架、DI 层或公开 SDK API。

保存行为的改变是 bug 修复，必须与单纯提取函数区分并写入 OpenSpec。迁移成本主要为私有 helper、autosave/导入保存调用与真实组合回归；资源保留和垃圾回收含义必须明确。不能把保存返回的精简 assets 安装回活动池而破坏 redo。

保存相关回归应保留历史、导入锁、导出元数据和项目名测试，再增加真实仓储接入 workspace 的 import→undo→save→继续编辑→切换/导出→reopen 及 redo 分支。返回输入的 save mock 不足以验证这个边界。

## 不采用的改造

App 组合各功能 hook 符合 Studio 的角色。React imperative handle 承担实例生命周期，转发代码本身不构成删除理由。viewport 确实协调事务和资源所有权，拆分必须解决具体合同问题。light-only 比较与持久化规范化的目标不同，不能盲目合并。无需改变 SceneDocument schema、hash/nodeIndex 或丢弃 redo 资源。

本结论只覆盖已检查的调用链，不构成全仓正确性保证。正式方案与实施结果见[改造过程](../remediation-log.md)和[保存设计](../../../../openspec/changes/persistence-safety/design.md)。
